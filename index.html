How it works
  • Karafka consumers on platform event topics build a player profile with 100+ fields.
  • 40+ trigger types, including schedules and per-bet triggers; actions for bonuses, comp points, tags, groups, notifications, lottery tickets and delays.
  • Actions are published to Kafka from Sidekiq jobs with retries, in batches of 1,000 players; validations cap node count and prevent loops.
Design & coordination

A trigger on every bet

Lets operators react to each individual bet (for example, a bonus after a big win) instead of waiting for a periodic recalculation.

~2.75 s
from bet to action
How it works
  • A batch Kafka consumer on game-round events groups bets per casino and matches them against pre-compiled trigger matchers.
  • In-process LRU caches with TTL hold compiled workflows and per-player counters; counters are flushed periodically and on eviction, rebalance or shutdown.
  • Cache invalidation is broadcast over Redis pub/sub.
Implemented

Scheduled waits in workflows

“Wait 3 days, then send the offer.” Pauses a workflow for each player and resumes it on time.

10k
jobs per bulk push
How it works
  • Added PostgreSQL to a MongoDB service: range partitions, created ahead and rotated by cron.
  • State machine: waiting → queued → started → finished / skipped / failed.
  • A periodic cron job picks up due delays and pre-enqueues upcoming ones via Sidekiq bulk push; a failure monitor watches for stuck delays.
